# Инженерный baseline

Это вход в skill-native выжимки, а не универсальный style guide. Материализуй
отдельный bounded basis для каждой активной lane и не передавай ей маршруты
других ролей.

## Приоритет

1. Явный запрос и утверждённые REQ/AC.
2. Ближайшие project instructions и архитектурный канон.
3. Автоматические правила проекта: formatter, linter, compiler, schema, CI.
4. Устойчивые паттерны ближайшего аналогичного кода и тестов.
5. Актуальная спецификация затронутого протокола.
6. Общая инженерная литература как проверочная линза.

Конфликт не разрешай молча. Зафиксируй обе стороны, влияние и владельца
решения. Не воспроизводи очевидную уязвимость или дефект только потому, что он
встречается рядом.

## Как загружать

1. Получи кандидатов командой `delivery_context.py route --task`.
2. Выбери для каждой активной lane один основной route по intent и поверхности.
3. Добавь второй route только для реально независимой поверхности той же lane;
   test может получить третий, если отдельно проверяет BE и FE/security surface.
4. Выполни `delivery_context.py materialize --assign lane=route --write
   <case-root>`; команда сама извлечёт только перечисленные headings.
5. Инициализируй case: `delivery_case.py init` сверит lanes, содержимое и hashes.
6. Перед запуском роли получи пакет через `delivery_case.py context --lane`.
7. В report укажи использованные rule IDs и проектное evidence.

## Граница применимости

- Выжимка не создаёт scope и не разрешает изменение.
- Источник не заменяет воспроизводимую проверку.
- Ссылка на стандарт не означает conformance всего продукта.
- Платный или недоступный норматив не пересказывается как будто прочитан.
- Версии и доступность смотри в `source-registry.md`.
