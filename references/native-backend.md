# Выжимка: backend и HTTP

Используй вместе с проектным API/data/error canon. RFC задаёт семантику HTTP,
но не навязывает стиль URI или JSON-полей проекта.

## B01. Ресурс, метод и наблюдаемая семантика

**Источник:** `RFC-9110`, §§3, 9.

- Отделяй идентичность ресурса от действия: метод несёт общую HTTP-семантику,
  URI — target в проектном namespace.
- Проверь свойства выбранного метода: safe, idempotent, cacheable, наличие и
  смысл content.
- Не маскируй изменение состояния под safe-метод и не обещай идемпотентность,
  если повтор может создать новый наблюдаемый эффект.
- Сверь routing/naming с ближайшими API-аналогами и style profile проекта.

## B02. Ответы, ошибки и representations

**Источник:** `RFC-9110`, §§6, 8, 15.

- Status code описывает итог обработки запроса; error envelope и domain code
  уточняют его в формате проекта.
- Зафиксируй представление успеха, validation/domain/auth/conflict/not-found и
  unexpected failure; не превращай всё в `200` с флагом ошибки без канона.
- Проверь отсутствие тела там, где протокол его не предполагает, и корректную
  интерпретацию content metadata.
- Ошибка должна быть безопасной для клиента и диагностируемой оператором без
  утечки секретов или внутренних деталей.

## B03. Совместимость и повтор запроса

**Источник:** `RFC-9110`, §§9, 13; `SWEBOK-4.0a`, Construction §1.2.

- Определи, что произойдёт при retry, timeout после обработки и дубликате.
- Для изменения представления проверь старых клиентов, optional/default поля,
  неизвестные значения enum и порядок rollout/migration.
- Если важна конкуренция обновлений, рассмотрение preconditions/validators
  должно быть явным; не добавляй их без продуктового контракта.
- Cache behavior, invalidation и `Vary` проверяй только на реально затронутой
  поверхности.

## B04. Data и transaction boundary

**Основание:** `SWEBOK-4.0a`, Construction, Testing и Quality KAs.

- Сверь schema/name/nullability/default/index/migration patterns с проектом.
- Зафиксируй атомарность и поведение частичного отказа на границе операции.
- Миграция должна иметь forward/backward совместимость или явный cutover plan.
- Test evidence должно охватывать сохранённое состояние, а не только HTTP-ответ.
