# Выжимка: construction, code health и review

Правила ниже — переработанные проверочные линзы. Они не заменяют инструкции и
автоматические правила целевого репозитория.

## E01. Минимальный проверяемый change

**Источники:** `SWEBOK-4.0a`, Software Construction §1; `SWE-GOOGLE-2020`, ch09.

- Разрежь работу так, чтобы один change имел одну объяснимую цель и обозримую
  поверхность риска.
- Удали из diff случайное форматирование, несвязанный рефакторинг и файлы,
  которые не нужны для REQ/AC.
- Малый diff — не самоцель: он должен быть завершённым, собираемым и
  проверяемым, а не прятать обязательную часть в «потом».
- В report объясни цель, границу и способ проверки change.

## E02. Construction for verification

**Источник:** `SWEBOK-4.0a`, Software Construction §1.3.

- Делай поведение наблюдаемым через публичный контракт, диагностируемые ошибки
  и разрешённые проектом logs/metrics.
- Сохраняй модульность и точки подмены зависимостей, необходимые существующей
  test strategy; не добавляй test-only API в продуктовый контракт без решения.
- Избегай конструкций, которые существенно усложняют чтение, review и
  изолированную проверку без доказанной пользы.
- «Можно протестировать» должно подтверждаться конкретным test seam и запуском.

## E03. Иерархия локального канона

**Источники:** `SWEBOK-4.0a`, Software Construction §1.5;
`SWE-GOOGLE-2020`, ch08.

Применяй в таком порядке:

1. ближайшие обязательные инструкции и утверждённая архитектура;
2. formatter/linter/compiler/schema/CI;
3. документированный style guide и owners текущего контура;
4. несколько ближайших аналогов того же типа;
5. общий baseline скилла.

Если уровни расходятся, не усредняй их. Зафиксируй конфликт, следуй более
сильному источнику и запроси решение, если результат меняет публичный контракт.

## E04. Разведка соседнего кода

**Основание:** project-first интерпретация `SWEBOK-4.0a` §1.5 и
`SWE-GOOGLE-2020` ch08–09.

До правки собери change-local выборку:

- ближайший аналогичный модуль/handler/component;
- его тесты и fixtures;
- naming, directory boundaries, dependency injection, errors и logging;
- конфиги formatter/linter/type checker/build;
- публичные schemas или generated code;
- при неоднозначности — несколько свежих изменений того же контура.

Один случайный файл не считается стилем. Различай устойчивое соглашение,
legacy-исключение и очевидный дефект.

## E05. Conformance matrix

**Основание:** traceable review из `SWE-GOOGLE-2020`, ch09 и ch20.

Для затронутых поверхностей верни строки:

| Surface | Rule | Evidence | Result |
|---|---|---|---|
| module layout | instruction/config/analogs | пути или команда | pass/finding/n-a |
| names/types | formatter/linter/analogs | пути или команда | pass/finding/n-a |
| errors/logging | architecture/analogs | пути и тест | pass/finding/n-a |
| public contract | schema/spec/analog | diff и проверка | pass/finding/n-a |
| tests | test guide/analogs | test path/run | pass/finding/n-a |

`n-a` требует причины. «Похоже нормально» не является evidence.

## E06. Независимое review

**Источник:** `SWE-GOOGLE-2020`, ch09.

- Reviewer не должен быть автором проверяемого change.
- Проверяй не только correctness, но понятность, согласованность с кодовой базой,
  тестируемость и соответствие заявленной цели.
- Self-review автора обязателен как подготовка, но не заменяет независимый gate.
- Замечание должно указывать конкретную поверхность, риск и воспроизводимое
  evidence; вкусовые предпочтения без project rule не блокируют change.

## E07. Автоматизируй механические правила

**Источник:** `SWE-GOOGLE-2020`, ch08 и ch20.

- Formatter, linter, type checker, schema validation и статический анализ имеют
  приоритет для механически проверяемых правил.
- Запускай scope-aware project commands; не заменяй их самодельным grep, если
  проект уже определил канонический gate.
- Не объявляй весь репозиторий чистым по проверке только изменённых файлов, и
  наоборот — отделяй baseline failures от новых.
- Новый check должен иметь приемлемую точность и понятный способ исправления.

## E08. Evidence проверок

**Источники:** `SWEBOK-4.0a`, Software Testing §5; `ISTQB-CTFL-4.0.1`, §5.3.

Для каждой команды сохрани:

- точную команду и cwd;
- target revision/worktree state;
- exit status и значимый итог;
- время/окружение, если результат от них зависит;
- baseline failure или coverage gap отдельно от change regression.

Зелёный self-report без читаемого результата не закрывает gate.
